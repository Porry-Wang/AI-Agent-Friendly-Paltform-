# 0 背景
**变化**：过去我们使用平台一般都是通过操作前台面板去手动执行， 而在AI时代随着Agent能力变强，大部分人习惯性直接使用Agent去自动完成任务。

**尝试**：面对这种使用习惯上的变化，平台侧也在思考是不是能够提供更好的方式供用户实现自己的需求。
比如可以提供SKILL的方式，将平台的一些API调用包装进去，那么用户装上这个SKILL之后就能够通过Agent去直接完成使用平台的目的了。

**改造**：但实际上平台的API是由不同的团队去开发的，其中有很多不规范的点，比如命名不一致、鉴权方式各异、报错语义模糊等问题。
那么当Agent去调用的时候就会出现一些问题，比如：调用失败、反复调用、失败一次就放弃重试等等。
为了让用户更好的使用Agent操作平台，就需要针对平台做一些AI化的改造。当前项目就是关于这个问题的思考以及一些具体方案的设计与实践。

# 1、目标

> 平台的本质是 API，页面只是其中一种客户端；AI 化的核心是把底层 API 及其供给方式（API / Skill / MCP）改造得让 Agent 读得懂、调得动、出错知道怎么办。

**目标**：让现有（陈旧）平台完成 AI 友好化（Agent-Friendly）改造，使 Agent 能更好操作平台能力。

**问题**：
 1. 传统平台 API 零散、鉴权方式各异、报错语义模糊，导致 Agent 调用时无法快速定位问题、无法快速恢复。
 2. Agent 调用是爆发式的，平台需加强权限、流量监控、限流配额，防止打爆底层。
 3. 传统「xxx not found」式报错不足以支撑 Agent 决策。报错需提供失败根因分类、系统抖动时的可重试指引（retry_after）、以及多次重试的兜底措施，让 Agent 一看就知道「为啥失败、要不要再试、下一步怎么办」。
 4. 平台对 Agent 调用无感知，难以知道成功率、难以发现 BadCase。需在 Agent 侧加 Hook 捕获调用链 → 分析所用 Skill 版本与配置 → 挖掘 BadCase → 回灌提升平台特性，构建一套自动化闭环（RSI，递归自进化）。
 5. 平台新推送的 Skill 版本出问题时，用户需能快速定位、快速恢复。需 Skill Manager 系统，让用户可操作具体 Skill 版本、实时回退。

# 2、方案推进
## 2.1 整体方案
先捋 API 的 “标准化 + 错误语义 + 埋点”，拿现成 skill 接一两个高频场景小范围试点，权限/限流护栏随试点同步上，评测和放量往后放。


## 2.2 分优先级方案
### 1 接口标准化 + 错误语义改造
**解决痛点：接口乱（命名/鉴权/请求体各搞各的）、报错给人看（Agent 分不清该重试还是放弃）。**

具体怎么做：

1. 不贪全量。先圈一个高频场景——"创建训练任务 → 查状态 → 看日志/指标 → 停止"，对应大概 8~12 个接口，试点前盘出清单。
2. 把这撮接口的差异列成对照表：workspace ID 的各种写法、有的 string 有的 int、鉴权/域名/请求体不一致的地方。
3. <u>定统一返回契约：</u>一个外壳包 ok / data / error / trace_id；错误里带 category（致命 / 抖动 / 配额）、retryable（能不能重试）、retry_after（等多久）、next_action（下一步干嘛）。大白话：让 Agent 一看就知道"这次为啥失败、要不要再试、下一步怎么办"。
4. <u>统一从网关出口</u>，老接口包一层适配转换，不强行重写底层。
5. 沉淀进 AF 规范文档，新接口按规范走。

**预期收益**：<u>Agent 不再靠猜，调失败知道怎么办</u>；这套契约后面所有场景复用。

资源/依赖：后端改造人力；统一网关【外部假设：复用 A 团队已有网关，否则要先搭】；底层接口负责人配合确认字段。

风险与规避：老接口牵一发动全身 → 用适配层包，不动底层；契约定不好反复改 → 先小撮接口验证再扩。

**衡量指标**：试点接口 100% 走统一契约；抽测一批错误场景，Agent 能正确分流（重试/放弃/上报）的判对率。



### 2 可观测埋点 + trace 串联
**解决痛点：本地数据盲区（只看到最后一次成功）、Agent 异构（各家 hook 不一样）。**

具体怎么做：

1. 在试点用的 Agent 里装 hook（大白话：Agent 提供的回调钩子，能在它调工具前后插一段我们的采集逻辑）。A 团队在各家装过，做法可复用。
2. 每次调用带 trace_id + session_id + skill 版本，把"同一个任务前后多次调用"串成一条链（trace 就是一次完整任务的调用链路）。
3. 采回来的数据清洗、打标（哪些跟本平台有关），落后台。
4. 先支持试点那一两个 Agent，别一上来全适配。

**预期收益：**<u>能看到"前面失败 9 次最后才成功"这种真实体验，badcase 挖得全。</u>

资源/依赖：hook 采集脚本；后台存储与清洗【外部假设：有可落数据的后台和基本清洗能力】；各家 Agent 的 hook 接口。

风险与规避：各家 hook 不一致 → 试点只挑一两个 Agent；可能采到用户本地敏感数据 → 先只采工具调用元数据，不采代码/数据内容【外部假设：隐私/脱敏边界需先界定】。

**衡量指标**：试点任务 trace 串联完整率；能复现"多次失败后成功"的链路；每日 badcase 能自动捞出。



### 3 试点最低护栏：权限 + 限流 + 危险操作确认
**解决痛点：突发流量 + 权限。危险操作确认属延伸，单独标。**

具体怎么做：

1. 给 Agent 发独立身份/委托令牌，带最小权限范围（大白话：Agent 拿一把只能开特定门的钥匙，不是万能钥匙）【外部假设：有可发令牌/鉴权的基础设施】。
2. 网关上限流 + 配额 + 熔断（限流=单位时间最多调几次；配额=总量上限；熔断=下游不行就短暂断开），防 Agent 爆发式调用打爆平台。
3. 危险操作（停止/删除任务）加事前确认【外部假设：破坏性操作保护（确认/审批/急停开关）属延伸能力，需另行设计】。
4. 试点期白名单用户 + 白名单操作，先不放删除类。

**预期收益：**<u>试点不会把平台打爆、不会误删人家跑了几天的任务。</u>

资源/依赖：鉴权/令牌系统【外部假设】；网关限流能力；确认交互（可先做简单的"二次确认"）。

风险与规避：护栏太严试点跑不动 → 白名单内先松后紧；令牌泄露 → 最小权限 + 审计留痕。

**衡量指标**：试点期零平台过载事故、零误删；限流触发时能正确返回 retry_after。



### 4 现成 skill 接试点场景
**解决痛点：上下文爆炸、skill 生命周期（部分）。**

具体怎么做：

1. 复用 A 团队 skill 做法，给试点场景写一个 skill（本质是个 markdown，把这几个接口怎么用、业务含义讲清楚）。
2. 用渐进式披露（大白话：先给一份精简目录，Agent 用到哪个工具再取它的详细用法，不一次性全塞）控制上下文。
3. skill 带版本号，接 Skill Manager（版本检查、更新、回滚）【外部假设：复用 A 团队 Skill Manager】。
4. 先发给白名单试点用户，收反馈迭代。

**预期收益：**<u>纯 Agent 党一句话就能创任务/查状态，不用切页面。</u>

资源/依赖：skill 编写人力；Skill Manager【外部假设：复用】；试点用户。

风险与规避：skill 写得不好 Agent 瞎试 → 靠 P0-2 可观测看真实调用再迭代；推错版本 → Skill Manager 回滚。

**衡量指标**：试点用户用 skill 完成任务的成功率；端到端耗时；人工接管次数。



### 5 性能/SLA 专项
**解决痛点：查询接口 4 秒太慢。**

具体怎么做：

1. 给试点接口定 SLA（大白话：响应时间承诺），查询类目标 ≤2s。
2. 把每个接口耗时打出来，揪出慢的。
3. 慢接口拉底层负责人一起看链路（性能优化是独立工作项、需跨团队配合）。
4. 先优化试点这几个，不全量。

**预期收益**：<u>Agent 串行等待不被慢接口拖死。</u>

资源/依赖：底层接口负责人时间【外部假设：能拉得动跨团队配合】；性能分析工具。

风险与规避：底层优化周期长 → 先把最慢的 1~2 个压下去，其余标"慢"让 Agent 异步轮询。

**衡量指标**：试点查询接口 P95 ≤2s（P95 大白话：95% 的请求都比这个快）。



### 6 评测 + badcase 飞轮
**解决痛点：评测空白、badcase 缺闭环。**

具体怎么做：

1. 建一个小 benchmark（大白话：一组固定测试任务 + 标准答案，用来给 skill 打分）【外部假设：有测试任务集和评判/标注人力】。
2. 每天从 trace 里挖 badcase（A 团队有挖掘系统，做法可复用）【外部假设：复用 A 团队挖掘系统】。
3. 修好 badcase → 回灌进 skill → 用 benchmark 验证变好 → 发版，形成飞轮。
4. 先覆盖试点场景，别一上来全量评测。

**预期收益：**<u>skill 改一版知道是变好还是变坏，质量能持续涨。</u>

资源/依赖：评测任务集 + 评判标准【外部假设】；挖掘系统【外部假设：复用】；数据分析人力。

风险与规避：评测标准主观 → 先定可量化指标（成功率/耗时/接管率）；标注成本高 → 先小集。

**衡量指标**：benchmark 分数随版本上升；badcase 从发现到修复回灌的周期。



### 7 规模化：多 Agent + 全量接口 + 正式治理
**解决痛点：接口不统一、Agent 异构、突发流量与权限治理只覆盖试点，需扩到全量。**

具体怎么做：试点跑通后，标准化契约扩到更多接口；适配更多 Agent（各家 hook 不同，逐个来）；护栏从白名单转正式策略；skill 按场景拆成多个。坚持灰度（大白话：先放一小部分用户/流量，没问题再扩），不一步到位。

**预期收益：**<u>从"一两个场景能用"到"平台能力普遍 Agent 可操作"。</u>

资源/依赖：前面各块成熟；更多人力。

风险与规避：全量上线风险大 → 灰度放量 + 可回滚。

**衡量指标**：覆盖接口数、活跃 Agent 用户数、整体任务成功率。



## 3、阶段划分建议
**试点验证阶段**  
核心目标：<u>证明"Agent 能安全地完成一个高频训练场景"。</u>  
交付物：标准化 + 错误语义的 8~12 个接口、一个试点 skill、hook+trace 可观测、最低护栏、白名单试点跑通报告。

**能力补齐阶段**  
核心目标：<u>把试点暴露的短板补上，质量变得可衡量。</u>  
交付物：性能达标、评测 benchmark + 飞轮跑起来、skill 版本管理成熟、badcase 闭环。

**规模化推广阶段**  
核心目标：<u>从单场景到多场景多 Agent，灰度放量。</u>  
交付物：更多接口标准化、多 Agent 适配、正式治理策略、多 skill、人才梯队。


## 4、取舍建议
前置：接口标准化 + 错误语义、可观测埋点、最低护栏。

可以先不做：全量接口标准化、多 Agent 全适配、完整评测体系、性能全量优化、成本计费/签名/模型回归这些延伸项。

建议：宁可场景少、Agent 少，也要把<u>"标准化 + 错误语义 + 可观测 + 护栏"</u>这条最小闭环做扎实。 贪多一步到位，返工更贵。



## 5、遗留待评估项
**延伸难题（需先调研评审）：**

+ 幂等/重复创建：Agent 重试会不会重复创任务烧卡，要不要加幂等键。
+ 成本归属/预算控制：自治 Agent 开实验卡时算谁的，要不要计费/预算闸。
+ hook 采集隐私边界：收本地 session 的脱敏/合规边界，需法务/安全评审。
+ skill 供应链安全：要不要签名校验防篡改。
+ 模型换代回归：底层模型升级 skill 漂移，要不要回归评测。
+ 责任归属/审计：Agent 自主操作出事谁负责，合规审计要求。

**资源类待确认（落地前必须拍板的外部假设）：**

+ 能不能直接复用 A 团队的网关 / Skill Manager / 挖掘系统；
+ 有没有可隔离的试点环境（sandbox）；
+ 拉不拉得动底层接口负责人配合性能优化；
+ 有没有评测任务集和标注/评判人力；
+ 有没有可发委托令牌的鉴权基础设施。
